# Activity 1 – Step 2: A specific prompt with context

**Chatbot / model:** ChatGPT (GPT-6.1 Sol) 

## Prompt

```text
Act as a professional software tester and suggest test ideas for the feature delimited by three hashes. All test ideas should be focused on discovering risks that impact the quality characteristics: Functionality, Data Integrity and Security
###
* As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.
* Acceptance criteria:
  - Upload should support the following common file formats: PDF, DOCX, TXT
  - The maximum file size should be 20MB
  - When a document is uploaded it should give a progress update to the user
  - Once uploaded, the document must initially be only accessible to the person who has uploaded it
  - A report of the upload and whether it was successful or not will be stored in the auditing feature
###
```

## Response

## Functionality

| Risk | Test idea |
|---|---|
| Supported documents are rejected | Upload known-good PDF, DOCX, and TXT files. Verify each completes successfully and appears in the uploader’s document list. Repeat with uppercase extensions and filenames containing spaces or Unicode characters. |
| The size limit is applied inconsistently | For each supported format, upload a valid file one byte below, exactly at, and one byte above the agreed 20 MB threshold. Verify the first two succeed and the last is rejected with a clear message. |
| Progress gives the user the wrong impression | Throttle the connection so intermediate progress is visible. Verify progress reflects the active upload and success appears only once the document is available. Interrupt the connection near completion and check that the interface shows a clear failure or recovery state. |
| Retrying creates unintended duplicates | Double-click Upload, then separately retry after a timeout that occurs just after the server saves the file. Verify the result follows the agreed retry behavior and the user can tell which uploads succeeded. |

## Data Integrity

| Risk | Test idea |
|---|---|
| A successful upload changes the file | Download each supported format as the uploader and compare its checksum with the original. Include a TXT file with non-ASCII characters and files near the size limit. |
| An interrupted upload leaves a partial document | Disconnect mid-upload and simulate a failure after file storage but before document registration. Verify no partial document is available and a retry can produce a complete file. |
| Files or metadata are mixed up | Upload different files with the same filename concurrently, using both the same account and different accounts. Verify each document ID points to the correct contents, filename, and uploader, with no unintended overwrite. |
| The audit trail disagrees with the result | Compare the audit report with the actual outcome for success, format rejection, size rejection, interrupted transfer, and storage failure. Verify the recorded outcome and attribution are correct. Simulate an audit write failure and check whether recovery preserves the required audit record. |

## Security

| Risk | Test idea |
|---|---|
| Another user can access a private document | Immediately after upload, try to find, preview, or download the file as another user in the same organization, a user in a different organization where applicable, and a signed-out visitor. Repeat using the exact document ID and a copied download URL. Confirm the uploader retains access. |
| A caller can bypass upload validation or choose another owner | Submit requests directly with an oversized file, an unsupported file renamed to `.pdf`, mismatched content and declared type, and a forged owner ID. Verify server-side validation and confirm ownership comes from the authenticated account. |
| Uploaded content or filenames can execute code | In a test environment, upload harmless security fixtures such as a PDF with embedded script and a filename containing HTML. Exercise document lists, previews, downloads, and audit views. Verify uploaded content cannot execute with the application’s privileges and filenames are displayed as text. |
| Temporary storage or audit records expose legal information | Attempt to access in-progress and failed uploads using temporary links or storage paths. Check that audit views enforce access controls and that audit records omit document contents, credentials, and reusable access links. |

Before running the boundary and audit tests, agree on the exact byte count for **20 MB** and which interrupted or rejected attempts must appear in the audit trail.
